# Риски, решение развилки и следующие этапы

## Риски 006

1. `NPCPlayer : BasePlayer` может существовать и иметь поля API, но конкретный prefab может не привязаться к RustNav, быть ограничен зоной монумента или переходить в sleeping state.
2. Native `PlayerInventory` может требовать настоящие player/network session или special ServerInit. Не создавать внешнюю учётную запись, не подделывать Steam ID настоящих людей.
3. Active item может быть валиден на сервере, но без клиента невозможно доказать видимую анимацию/внешний вид. Не говорить «как живой игрок» на основании GetHeldEntity() без client smoke.
4. Переключение actor на player-derived может сломать движение/пулы/клановую логику; не мигрировать 001/003/004/005 до прохождения gates.
5. Для фиктивного native equip нельзя выдавать бесплатно «скрафченный stonehatchet из 005» в другом мире. Для 006 допустим честно обозначенный test fixture; игровая экономика не входит в scope.
6. Ограничение новых E2E двумя (третий только за доказанное исправление) — критично для времени/лимитов. При настоящем engine blocker нужен архитектурный вывод, не 20 бессмысленных попыток.

## После решения 006

- **Если GREEN:** продумать компактный bridge от persistence/экономики Gen2 к player-derived avatar; затем проверить реальное удержание/износ оружия/экипировки и только после этого игроковый combat/native queue. Не массово переносить код до регрессионного E2E.
- **Если PARTIAL/BLOCKED:** сохранить Gen2; задокументировать конкретный план native player workaround или честные server adapters. Не продавать отдельные NPC как единое player model.
- **Независимо от результата:** перед долгоживущим населением нужна следующая задача `WORLD-ECONOMY-PERSISTENCE` — world-keyed source depletion и crash-safe debit/craft, обязательный контроль повторного фарма после рестартов. Потом полноценные bench/blueprint/research, первые house/TC/maintenance/home-local nav, спалки/смерть/respawn, боевые группы, рейды и Giant Excavator. Приоритет задан реальными рисками, а не количеством «GREEN».

Будущие задачи — каждый раз **отдельный архив и отдельный новый диалог Codex с /goal**, а после каждого отчёта — независимая сверка итогового коммита, кода и `RESULT.md` через GitHub. Не сливать множество фич в один бесконечный чат.
