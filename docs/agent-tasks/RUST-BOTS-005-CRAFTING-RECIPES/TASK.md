# RUST-BOTS-005 — первый реальный крафт и ограничения рецептов

## 0. Outcome

На одном собственном изолированном Rust Dedicated Server один Gen2 NPC должен **сам принять решение, добыть достаточное количество настоящих ресурсов, изготовить полезный предмет по рецепту из текущего установленного Rust и сохранить результат после полного restart**, не увеличивая суммарные предметы без оплаченного источника. Проверить хотя бы один **недоступный рецепт** (ингредиентов/выученного blueprint/верстака не хватает) — отказ **до любых списаний и выдачи**. Результат честно пометить `NATIVE_PLAYER_CRAFTING` либо `SERVER_ACCOUNTED_CRAFT` на основании фактического API/live, не по внешнему сходству.

Выполнить одним укрупнённым gameplay slice; **не строить** в 005 полноценную мастерскую/базу, PvP, систему кланов, гигантский tech tree и PlayerInventory replacement. Достижимость каждого шага определяется API gate. Если native путь не поддерживается Gen2, разрешён ограниченный **SERVER_ACCOUNTED_CRAFT**; это полезный результат, но не эквивалент настоящего player craft queue.

## 1. Read / API gate перед реальным запуском (обязательный)

1. Прочитать `AGENTS.md`, 001/003/004 результаты, `API_DECISION.md` 004, `LIFE_ROADMAP.md`, текущие исходники и скрипты. Зафиксировать local HEAD, origin/master, installed DLL/API fingerprint без запуска SteamCMD.
2. Изучить реально установленную `Assembly-CSharp.dll` и API/IL `ItemBlueprint`, `ItemDefinition`, `ItemManager`, `ItemCrafter`, `PlayerInventory`, `PlayerBlueprints`, `Item`, cost/amountToCreate, blueprint default/learned state, workbench level/proximity, native queue. Не переносить recipe prices из вики или устаревших версий; фактические cost/requirements читать из loaded runtime. Отделить static/IL от live evidence.
3. Оценить: можно ли *с текущим Gen2 actor* использовать player-native crafting, native blueprints, нативные верстаки? Наличие `PlayerInventory.crafting` у BasePlayer само по себе не означает эквивалентность. Статически сравнить с NPCPlayer/BasePlayer и дать решение о будущем avatar bridge, **не срывая scope 005** дорогим переходом actor, пока нет проверяемого преимущества.
4. Выбрать **существующий** доступный нулевого уровня верстака (или доступный по фактическим правилам) рецепт полезного предмета. Приоритет предмету с **wood и stones**, например stone tool, *если реальный runtime рецепт таков*; иначе другая полезная реально разрешённая item blueprint с физически добываемыми ингредиентами. Не выдумывать рецепт и количества. Указать exact item shortname, item id, blueprint, amountToCreate, ingredients, craft time (если используешь), blueprint unlock policy, workbench level и причина выбора.
5. Выбрать реально существующий пример **запрещённого** рецепта — требующий неизвестный blueprint, отсутствующий верстак или ингредиенты. Зафиксировать фактический runtime gate. Утверждать native enforcement только если native API проверен; для адаптера это серверная проверка установленных правил.
6. В `API_DECISION.md` (новый 005) перечислить `SUPPORTED / STATIC_ONLY / LIVE_PROVEN / UNSUPPORTED / UNKNOWN`, режим реализации и причины. Не тратить live бюджет на пустые экспериментальные пробные спавны.

## 2. Gameplay — реальная причинная цепочка

- Один NPC с честным базовым rock (или доказанным исходным kit). По поведению `NeedItem → SelectBlueprint → DetermineIngredients → DiscoverNaturalSources → RustNavTravel → Harvest → CheckInventory → GateBlueprint/Workbench → Craft → Verify → Save`. Точные координаты источников и цели не хардкодить. Выбор ресурсов по дефициту реальных ingredient counts; bounded discovery/route/hits и stuck recovery.
- Использовать существующий source debit/condition pipeline из 004; исключить двойное начисление и спавн фиктивных ресурсов. На natural source требуются source IDs/prefabs, debit after hit, учёт condition. Зафиксировать, что native resource pool depletion across restart не доказано в 004; не молча обещать полную постоянную экономику.
- **До создания output:** проверить inventory actual quantity by shortname/item id, blueprint default/learned state и актуальный workbench gate; проверить, что world actor находится в допустимом рабочем контексте; не использовать «универсальное разрешение» для всех рецептов. Оплата должна следовать установленному рецепту с правильным output multiplier. Для позитивного сценария предпочтителен default known low-tier recipe, не требующий невыполненных исследований или верстака.
- Крафт через native queue/recipe pipeline, **только если** реально работает на выбранном actor и учитывает ресурсы/разблокировки. Иначе адаптер `SERVER_ACCOUNTED_CRAFT`: синхронное списание **существующих Item**, проверка exactly consumed UID/amount, потом `ItemManager.Create` exact item/quantity, `MoveToContainer` и проверка output/UID. Не делать `GiveItem` без debit; не создавать готовый предмет для скриншота. Если failure между debit/output, фиксировать irreversible partial и не удваивать award, не писать ложный rollback. Проверить inventory conservation per shortname (с учётом **документированной** трансформации рецептом).
- Проверить negative gate **на живом runtime** по реально установленным blueprint/workbench/ingredients. Попытка должна вернуть DENIED и иметь **нулевые item/pool changes**. Нельзя искусственно объявлять закрытым рецепт, который на самом деле открыт; фиксируй actual reason.
- Новый созданный предмет сохраняется в owned native ItemContainer с корректными stack/condition/UID. Выученные знания сохраняются **только если были реально изменены** по поддержанной модели; не писать «blueprint learned», если не реализовывали. Не смешивать mock persistence и live.

## 3. Restart и экономика

- После успешного CRAFT полный штатный `quit`, native world save, verified snapshot для inventory + actor goals/identity + inventory/key/world proof согласно 003/004; **второй отдельный процесс** загружает проверенный snapshot и подтверждает exact UID/amount/condition, изготовленный предмет, отсутствие повторного крафта и повторной выдачи starter kit.
- Даже если source pool after restart снова полный (ограничение 004), **не выдавать** его как «сохранённую добычу». Запретить в RESTORE-сценарии новый harvest/craft; зафиксировать долговременный риск и конкретное техническое решение на будущее: durable idempotent depletion transaction ledger привязанный к world identity/entity stable key/generation, либо другая реально проверенная интеграция. Исправление source pools можно делать в 005 **только если** это не раздувает scope и E2E бюджет; иначе отдельная следующая задача.
- Сохранить точные суммы потраченного и полученного, причины отказов и unspent ingredients, включая UID partial stack debit. Проверить отсутствие повторного output при повторном вызове craft. Потеря UID в результате легитимного расхода не считается багом, но должна быть объяснена и доказана.

## 4. Код и интеграция

- Реиспользовать `src/plugins/RustBotsSurvival.cs` и proven runner. Допускается новый маленький реальный helper, но не клонировать 004 в четвёртый огромный plugin. Новый тестовый режим `-SurvivalCraft` (или эквивалент) должен быть взаимоисключающим с другими и не ломать старые 001/003/004; отдельный `CRAFT/RESTORE` статус, validator и focused tests. Приоритет простому обслуживаемому C# 7.3 и minimal incremental code.
- Перед первым live — compile/fixtures: отсутствие recipe, missing ingredients, wrong blueprint/workbench, double debit, interrupted output, wrong amount, UID/condition mismatch, replay crafted item; режимы legacy 001/003/004 должны оставаться проверяемыми.
- Максимум **2** контролируемых live server runs (craft+restore); **3-й разрешён только при доказанном конкретном дефекте**, после offline исправления. Не повторять сервер ради некритичного оформления отчётов. Сохранять full stdout/log, plugin-result.json, inventory/state snapshots и hashes в ignored `.local/`.
- Никаких fake E2E, фиктивных методов native GUI, визуальной анимации/реальной экипировки/сессии. Для `GEN2` не заявлять эквивалентность player-held tools и player craft queue.

## 5. Safety / Git / QA

- Пользователь **заранее разрешил** commit и обычный push в `master` для этой задачи. Перед правками проверить `master == origin/master` и clean status; на конфликте/чужих изменениях не очищать/переписывать историю. `git add` только exact allowlist, `git diff --cached --check`, check-ignore/ls-files `Server/`, public secret scan. Никаких force, reset, rebase, clean, broad add или неожиданного network/app update.
- Сохранять owner `Server/` read-only, worlds/oxide/config/data/mods и оригинальные BAT. Работа только в собственной copied test installation. RustDedicated запускать **самому**, без инструкций владельцу. Применять текущую временную firewall isolation и Job Object; не оставлять PID, helper, открытые TCP/UDP порты, firewall rules или lock. Не закрывать чужой процесс. Если изоляция не доказана — fail closed.
- Проверить mojibake отдельно от escaped Cyrillic; русские и украинские тексты хранить корректным UTF-8. Публичные доказательства обезличить; не публиковать IP/Steam ID/реальный owner seed/name/password/local private configs. Сырые logs `.local/` ignored.
- В `RESULT.md` честно отдельные `NATIVE_PLAYER_CRAFTING`, `SERVER_ACCOUNTED_CRAFT`, `BLUEPRINT_GATE`, `BENCH_GATE`, `INVENTORY/CONSERVATION`, `PERSISTENCE`, `NAVIGATION`, `SAFETY`; `GREEN/PARTIAL/BLOCKED/FAILED`, refs raw receipts, environment versions, timing, before/after costs and output, source provenance, cleanup, file allowlist and push SHA. Сопоставить state with code, не выдавать test fixtures за live доказательство.

## 6. Приоритет

Главное — **изготовленный за реальные ресурсы полезный предмет и корректный restart**, а не расширение инфраструктуры. Если native player craft физически невозможен для Gen2, выполнить проверяемый accounted adapter, указать технологический долг. Склады/верстаки/исследование чертежей/базы/смерть/PvP — следующие уровни после успешного 005. Не делать 002 updater.
