# RUST-BOTS-008 — восстановление PlayerInventory и HeldEntity без конфликтов сетевых ID

## Цель, scope, бюджет

Получить **один проверяемый жизненный цикл** `ScientistNPC : BasePlayer`: после подтверждённого JOURNEY с native добычей и честно изготовленным топором в том же игровом мире выполняется **независимый запуск RustDedicated**, в котором восстанавливаются те же логическая личность, предметные UID, amount/condition, контейнеры/слоты, активный UID изготовленного `stonehatchet` и новый законно принадлежащий этому NPC `HeldEntity`. Не создавать заменяющий `Item` с новым UID и не требовать старый сетевой ID held entity. Никакой оплаты/добычи/крафта в RESTORE.

**Бюджет:** целевой 1–2 полноценных live server runs; максимум 3 только при конкретном дефекте, зафиксированном и исправленном по результатам предыдущего запуска. До старта сделать API/IL audit и offline негативные тесты. Пользователь ничего не запускает вручную. Не менять работающие 001–006 без необходимости.

### Шаг A. Диагностика на сохранённом evidence

1. Сверить `master`/GitHub SHA, local status, `AGENTS.md`, целостность installed DLL, 006/007 docs/code, логи/JOURNEY/RESTORE в ignored `.local` без изменения raw результатов.
2. Прочитать реальные IL/metadata установленного `Assembly-CSharp.dll`/`Rust.Data.dll`: `PlayerInventory.Save/Load/Initialize/Strip`, `ItemContainer.Load`, `Item.Save/Load`, `ItemModEntity.OnParentChanged`, `Item.RecalulateParentEntity`, `HeldEntity.SetupHeldEntity`/ownership, `NPCPlayer.ServerInit`, `BasePlayer.UpdateActiveItem`, временные `heldEntity`, `worldEntity` и смысл `NetworkableId`. Не предполагать их lifecycle по похожим названиям.
3. Выполнить read-only inspection сохранённого `PlayerInventory` protobuf: ровно ожидаемые main/belt/wear, реальные Item UID/slot/condition, ссылки `rock` UID81010→held81011, `stonehatchet` UID87251→held87252, worldEntity=0, nested none. Если локальные файлы недоступны, честно фиксировать отсутствие и строить новый доказанный snapshot.
4. В isolated test root при коллизии `serverEntities.Find(81011)` записать (без персональных данных) **тип, prefab, net ID, parent net ID, owner net ID, associated item UID, IsDestroyed, in test world vs probe-owned** до изменения. Не считать mere ID collision доказательством чужого ownership. Подтвердить, что это временная ссылка из предыдущего процесса, а не разрешение на перенос чужого объекта.

### Шаг B. Безопасный алгоритм восстановления

1. Сначала валидировать immutable source snapshots + exact compatible world/generation/.sav/hash + предыдущее clean shutdown; Item UID должны отсутствовать глобально на момент восстановления, не должно быть другого живого avatar с тем же логическим ActorId.
2. Разделить долговечную сущность **Item.uid** и временную сетевую сущность **HeldEntity.net.ID**. При доказанном ephemeral характере ссылки можно очистить **только соответствующие поля в уже валидированной in-memory копии protobuf** до `PlayerInventory.Load`, оставив исходный binary snapshot/JSON/old run receipts неизменными. Не обнулять произвольные поля, не переписывать UID/слот/condition/amount и не удалять/перепривязывать чужой `serverEntities`.
3. Правильный native lifecycle: восстановить main/belt/wear, проверить native `GetOwnerPlayer()`, каждый Item UID и корректные role/slot; при необходимости только доказанные нативные методы parent lifecycle. Пересоздание **HeldEntity** допустимо штатным native путём как новая временная сущность; создание нового Item вместо исходного запрещено. Никаких manual `SetParent`, `forcedOwner`, fake Steam ID, fake API/визуальных claims.
4. Выбрать записанный `ActiveUid` через guard native belt lookup и вызвать `UpdateActiveItem`. Проверить `GetActiveItem()`, `GetHeldEntity()`, `held.GetItem().uid`, `held.GetOwnerPlayer()==npc`, `held.GetParentEntity()==npc`, native held flag, отсутствие dangling/stale reference, отсутствие повторно созданного `Item` и одинаковое состояние спустя несколько native ticks.
5. Строго различать новый **сетевой net ID созданного NPC/его held entity** и неизменные **Item UID** и `ActorId`: новый native NPC — допустимый представитель той же сохранённой логической личности, не «та же непрерывная Steam-сессия».
6. Если IL допускает несколько подходов, выбрать самый простой и проверяемый. При неоднозначном ownership, реальном foreign entity alias, повреждённом snapshot или ненадёжной нативной инициализации — FAIL CLOSED с явным `PARTIAL/BLOCKED`. Не ослаблять защиту ради GREEN. Прямой `Kill` существующей чужой held entity запрещён.

### Шаг C. Раннер, доказательства и регрессии

1. Сохранить `-AvatarSurvival` и `-AvatarSurvival -RestoreFrom <run-id>`, поправить только необходимые скрипты валидатора/проверки. Восстанавливать 007 JOURNEY **только если exact source proof/world/save/generation остаются валидными**. Не допускается обход hash/sav проверки или молчаливое копирование старого мира. Если кеш изменился после 007 RESTORE — один новый успешный JOURNEY, затем независимый RESTORE.
2. Offline RED→GREEN fixtures: сохранённая transient ссылка совпала с не принадлежащим боту живым net ID; старый HeldNetId отсутствует; source Item UID уже существует; повреждён snapshot; не совпал world/generation/hash; неправильные slot/role/condition; duplicate Item UID; попытка взять foreign UID; duplicate craft/kit/replay; нативное восстановление не породило held; race/cleanup. Fixture не заменяет live.
3. LIVE проверка: полный `PlayerInventory` main/belt/wear, только UID исходного snapshot, exact amount/condition, нет новых `Item` из воздуха, нет harvest/craft/kit в RESTORE. Активный `stonehatchet` имеет исходный Item UID, новый HeldEntity принадлежит новому NPC. Записать native restore before/after, raw owner/parent IDs, reconstruct per-item ledger, delta world item counts. Если нужен ещё один реальный movement leg после восстановления — только короткий, при достаточном времени; сам restore/held proof важнее.
4. RESTORE GREEN только при выполнении всех acceptance gates **после настоящего нового server process**, не на основании документации 007, offline compile или одинаковых JSON без native Load. Сохранить негативные исходы исходных запусков неизменными.
5. При каждом живом старте Codex сам контролирует временный firewall helper, отдельный test install, независимый Oxide writable state, RustDedicated не от admin, свой kill-on-close Job Object, bounded timeout/quit/save, проверку PID/портов/правил/leases/locks. Никаких чужих PID, SteamCMD, update/validate или изменения owner `Server/`.
