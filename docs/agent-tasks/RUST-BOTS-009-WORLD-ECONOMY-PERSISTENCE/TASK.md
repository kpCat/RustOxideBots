# TASK 009 — доказуемая долговечность экономики мира и идемпотентный крафт

## 0. Outcome и техническая граница

Один `ScientistNPC : BasePlayer` **нативно** добывает wood/stones с NATURAL `TreeEntity`/`OreResourceEntity` и честно расходует ресурсы на рецепт. В изолированной совместимой test world запасы этих же природных узлов должны после полного RustDedicated restart быть восстановлены **на корректном уровне depletion**, а не возвращаться к первоначальному pool и позволять фармить ресурсы повторно. Выполнить durable journal реального источника + расхода/результата и запретить повторную выдачу крафта. Доказать не «предметы после restart», а **источник + получатель + платёж + повторяемость**.

Цель укрупнённая, но ограниченная. Доводить до полноценной универсальной экономики для всех деревьев мира/50–100 NPC не требуется; по возможности сделать reusable слои без speculative фреймворков. Никакой симуляции «истощение наверняка сохранилось» и никакой публикации owner данных.

## 1. API / IL gate до live запуска

1. Читай `AGENTS.md`, все файлы 009 и 007/008 source/reports. Прочти установленный `Assembly-CSharp.dll`/`Rust.Data.dll` через существующий инспектор: `ResourceDispenser`, `ResourceEntity`, `TreeEntity`, `OreResourceEntity`, native `DoGather`, содержимое/`fractionRemaining`, обновление категорий, seed-based source recreation, resource respawn and node destruction, `PlayerInventory.Save/Load`, `ItemManager`, `ItemCrafter` отсутствие в Roam prefab. Документируй фактические методы и их побочные эффекты, а не переноси старые примеры из сети.
2. Выясни, **какой ключ узла действительно стабилен** через независимый restart. NetID, порядковый индекс списка, Item UID и одна округлённая координата НЕ могут по умолчанию считаться постоянным source ID. Выделяй `world fingerprint/cache generation/map+seed+size`, exact prefab/type, position (с обоснованным допуском), geometry/rotation/topology и доказательства one-to-one match. Если после restart кандидатов 0/2+ или существует риск отождествить новый respawn с прежним узлом — не корректировать чужой source, выдать `AMBIGUOUS_SOURCE` и PARTIAL/BLOCKED.
3. Проверь native `.sav`: содержит ли реальные fields resource pool и при каких условиях они могут восстанавливаться сами. Не предполагать, что `Server.Save()` сохраняет dispatcher pool. Учти законный engine respawn узла: старое depletion нельзя навечно накладывать на новые поколения ресурса.
4. Опиши проверенную стратегию durability: журнал с version/schema, world key, source identity/incarnation, исходным и текущим реальным native pool, tool condition, credited Item UID/amount, actor identity, craft intent, expected/actual inventory fingerprint, lifecycle/timestamps и integrity. Документ `API_DECISION.md` с фактами IL и зонами UNKNOWN.

## 2. Экономика: source journal / восстановления

1. Реальный ACTION: боту требуется добыть материалы (можно один ограниченный completed wood/stone episode, не весь 007 заново, но без бесплатных ресурсов). Использовать доказанный native `NATIVE_PLAYER_GATHER` через настоящий player-derived NPC, его held rock и `ResourceDispenser`. Никаких free ItemManager.Create для добычи/подмены; если native не работает, adapter только с явным source debit и status, при этом не считать native equivalence.
2. До необратимого native hit безопасно зафиксировать намерение/исходное состояние, после hit — точные native source pool before/after + inventory credit + tool wear с уникальным `transaction/action id`. На диске journal не должен оказаться как завершённый до фактической оплаты. Не полагаться на атомарность двух разных файлов/движка; use flushed versioned durable write and check hash/corrupt/torn-tail. Проясни, в каких окнах после crash доступен только `IN_DOUBT`, и **не делай повторное вознаграждение автоматически**.
3. После GRACEFUL quit записать proof journal + соответствующий native world `.sav`/generation/inventory/actor snapshot; runner связывает SHA и происхождение с конкретным завершённым run. Не редактировать прежние 007/008 raw artifacts, не использовать owner .sav.
4. На независимом RESTORE: сначала существующий strict world/inventory/held gate 008, затем **после готовности мира и ресурса** найти точно соответствующий NATURAL узел. Сравнить native pool с recorded expected: если уже равен — NOOP; если доказанно reset выше expected — применить ровно недостающий debit **один раз** с native-compatible update/fraction; если ниже expected/несовместим/двусмыслен — fail closed. Валидировать actual before/after, отсутствие влияния на соседние узлы и непротиворечивый journal. Не менять resource pool вслепую только по ID/позиции.
5. Повторный replay того же journal на том же runtime/source обязан стать NOOP, а не вторым списанием. После restart бот имеет прежнюю логическую identity и Item UID/состояние, **не переигрывает** добычу и не получает дополнительные ресурсы. Отдельная негативная проверка: чужой world fingerprint/поколение или подменённый prefab/position/corrupt journal отвергается без мутаций.
6. Если источник физически исчез между рестартами/возродился заново, задокументировать state и ограничение; не поощрять неверный GREEN. Данные о native respawn должны иметь отдельные понятные критерии. Безопасное значение отказа — сохранить доказательства, не выдавать лут и не удалять/создавать чужие узлы.

## 3. Крафт: intent, replay и crash window

1. Использовать доказанный рецепт `stonehatchet` из установленного runtime: реальные blueprint ingredients, не hardcode для исполнения, отсутствие доступного native `ItemCrafter` — честно `SERVER_ACCOUNTED_CRAFT`. Сохранить нативное списание UID и один produced Item UID/condition/active held, существующие 007/008 guards.
2. Выделить понятное состояние транзакции `PREPARED → DEBITTING/DEBITED → OUTPUT_CREATED → COMMITTED`, уникальный intent и receipts before/after. На duplicate intent или попытке повторного RESTORE — ноль новых Item/отрицательных изменений. Для `DEBITED` без гарантированно наблюдаемого output после crash — **IN_DOUBT/QUARANTINED**, без бесплатного перевыпуска, пока exact reconciliation не доказан. Не «исправлять» пропажу бесплатной выдачей.
3. Offline fault injection с контролируемыми точками до debit, после debit, после output, до durable commit; проверка не создаёт двойной output. Примеры ошибок: недописанный journal, wrong world ID, несовместимый recipe fingerprint, повторный intent, частичная оплата, чужой Item UID. Fail-closed не равен production crash atomicity: в отчёте отдельная классификация `CRASH_RECOVERY=OFFLINE_ONLY` или `LIVE_PROVEN`.
4. Если получится провести корректный bounded live crash/restart/fault experiment на **только собственном тестовом Job** без нарушения safety, делать в пределах бюджета и подтвердить ledger. Если нет — не выдавать статический fault тест за реальный interrupted-process recovery; ограниченный общий GREEN допустим только с явным `CRASH_ATOMIC=NOT_PROVEN` и `GREEN_WORLD_DEPLETION` (см. ACCEPTANCE).
5. Любая неоднозначная полуплата/половина готового выхода должна блокировать автоматический retry данного intent; raw evidence сохраняется. Не заявлять транзакционность всего Rust engine.
