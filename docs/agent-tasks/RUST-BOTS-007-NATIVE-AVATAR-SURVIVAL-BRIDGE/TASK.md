# RUST-BOTS-007 — Player-derived Survival Bridge + Crafted Held + Restart

## Цель / критерий пользы

Не новый абстрактный движок и не десятки микрофич. Создать **один проверяемый end-to-end игровой эпизод на одном `ScientistNPC : BasePlayer` actor**, объединяющий доказанные в 004/005 gathering/crafting с доказанной в 006 native player inventory/held, с независимым restart recovery. Такой переход нужен **до строительства и PvP**, иначе будем годами наращивать server-adapters в отрыве от персонажа с PlayerInventory.

Проверить local HEAD, публичный `origin/master` и git status до мутаций. Если base отличается, оценить фактическую историю, не делать reset/rebase/force/clean/stash и не затирать чужие изменения.

## Scope 007: одна личность, одна физическая модель

1. **Аватар и старт.** Использовать единственного `ScientistNPC : BasePlayer` из проверенного в 006 Roam prefab. Настоящие main/belt/wear, активный предмет/HeldEntity, RustNav. Применить исправления scheduler/wake и восстановление `agent.speed` после SetDestination. Не использовать второй скрытый Gen2 actor, dual-avatar, фальшивые SteamID, телепортации, MovePosition и невидимый отдельный склад как замену PlayerInventory. Для теста после native spawn определить и _безвозвратно исключить из baseline_ default Scientist loadout (боевое оружие/meds/системная одежда), оставив явно раскрытый стартовый rock/torch из действительного игрового kit (при возможности через player inventory native путь). Если native reset/loadout нельзя безопасно нормализовать, не называть это «спавном бомжа», а дать PARTIAL + диагностику.
2. **Единая логическая идентичность.** Дать стабильный, не-Steam `ActorId` (UUID/namespace) и простой state `NeedResource -> Move -> Gather -> Craft -> Equip -> Save/Restore`. Никаких координат/UID из прежних 004/005 запусков, никаких предзаготовленных stonehatchet. Данные о новом actor, inventory, активном UID и намерениях должны принадлежать **одному** NPC.
3. **Настоящая добыча.** Из мира на выбранной процедурной тестовой карте искать натуральные дерево и stone/ore (не fixture). NPC физически подходит к доступному источнику, проверяет RustNav complete path, grounded/range/LOS/ownership, реально расходует source pool для 200 wood и 100 stones по фактическому рецепту. На BasePlayer-аватаре сначала исследовать native `BaseMelee` gather: если live Native Player Gather дает предметы честно, использовать его и учесть штатные server modifiers; если нет — применить строго `SERVER_ACCOUNTED_TOOL`, адаптированный из 004, **с предварительно проверенным native pool debit, инструментом/износом и запретом double-yield**. Числа добычи брать из actual loaded blueprint, а не хардкодить расчёт. Если естественного source нужной категории нет/он недостижим, PARTIAL, не выдавать фиктивный результат.
4. **Настоящий крафт и экипировка.** Прочитать `ItemBlueprint` установленного `stonehatchet` и фактические gates. Списать точные native Item UID/amount со штатного `PlayerInventory` (belt/main; wear не считать ингредиентами без игрового основания). Предпочесть native ItemCrafter при реальной работоспособности; если он требует клиентского контекста и не подходит NPC, честно `SERVER_ACCOUNTED_CRAFT` из 005 с защитой от повторной оплаты/выдачи. **После крафта именно вновь изготовленный stonehatchet UID** должен переместиться в native belt, пройти guarded `UpdateActiveItem`, дать `GetActiveItem().uid == craftedUID`, `GetHeldEntity` -> BaseMelee, нативные owner/parent равны этому же avatar, held flag корректен. Нельзя подставить `TEST_FIXTURE stonehatchet` или старый UID 65008. Проверить отказ для отсутствующего/чужого UID, отсутствие инъекций и повторного output.
5. **Перезапуск.** На clean native quit/complete world save + hash-bound snapshots создать **новый RustDedicated-процесс** с совместимым world cache, восстановить ту же logical identity (вновь созданный native bot-id/netID допустим). Восстановить **точные** native item UID/amount/condition/maxCondition + container roles и выбранный active crafted stonehatchet; после native restore, `GetHeldEntity` должен принадлежать новому actor, не исчезнуть и не создать второй crafted UID. Не повторять start kit, gather, craft и output. Если не удается восстановить PlayerInventory UID корректно, PARTIAL и точная причина, а не создание нового «похожего» топора.
6. **Негативные кейсы и безопасность.** Недостаток материалов не должен создавать предмет; blueprint/workbench gate должен исполняться согласно текущему рецепту и условиям без фальшивого native claim; чужой/несуществующий UID не активируется; запрещен дублированный craft intent; плохой snapshot/foreign world generation блокирует restore до записи; неизменны сторонние игроки/дом/конфиги. Никакого вмешательства в owner Server или массового изменения исходников 001–006.

## Бюджет и план реализации

- Прежде чем запускать тяжёлый сервер, прочитать `API_GATE.md` и код 004–006, сделать metadata/IL audit и офлайн компиляцию C# 7.3; добавить focused tests/validators, проверяющие ложноположительные сценарии. Документировать фактическое решение `API_DECISION.md`.
- Рекомендуется небольшой, реальный bridge в `src/plugins/RustBotsAvatarSurvival.cs` (или аккуратно расширить 006/005 с мотивировкой). Не дублировать целиком 500+ строк каждого старого тестового плагина. Реиспользовать изолированный runner, валидаторы, кеш и Job Object; прежние `-PlayerAvatar`, `-SurvivalCraft`, `-SurvivalGather`, `-WorldRoam` и 001 сохраняют поддержку. Изменение кода должно быть локальным, без Harmony и модификации Rust DLL.
- **Live E2E: целевые 2 запуска**: добыча→крафт→экипировка, затем независимый RESTART/RESTORE. **Максимум 3-й**, если конкретный реальный defect в первых двух доказан и исправлен. Ранние static/fixture тесты обязательны; нельзя расходовать лимиты на бесконечные серверные прогоны. Один сложный gameplay slice важнее косметической полировки вспомогательных скриптов.
- Не использовать искусственный «успех», ручное перемещение актёра, скрытую выдачу предметов, соединение реального пользователя, чужие права/Steam идентичности, дублированный actor либо непроверенные native APIs.
- Если native attack/gather/queue не работает, сообщить точную причину, продолжить честный accounted режим, **не теряя основную цель**: crafted UID native-held by actual BasePlayer avatar + persistence. Native visual animation не заявлять без клиентского E2E.
- Не пытаться в 007 делать base/TC/doors/cupboards/raid/PvP/excavator, 50–100 bots, исследование техдерева, production resource depletion/crash journal. Учет resource depletion после рестарта обязательно оформить отдельным риском и explicit next gate; не объявлять production-ready, пока source pools могут восстановиться. `RISK_REGISTER.md` обязателен.
