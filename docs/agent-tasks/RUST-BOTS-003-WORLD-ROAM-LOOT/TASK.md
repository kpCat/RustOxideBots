# RUST-BOTS-003 — WORLD ROAM & FIRST REAL LOOT

**Статус:** новая задача, исполнять отдельным новым диалогом Codex. **Предыдущая работа:** RUST-BOTS-001 завершена GREEN; RUST-BOTS-002-SAFE-RUST-OXIDE-UPDATE существует только как DESIGN ONLY, НЕ начинать в рамках 003.

## 0. Главная цель

После доказанного движения `ScientistNPC2` на 92,2068 м создать первый наблюдаемый жизненный сценарий **одного** NPC на чистом изолированном RustDedicated: выбрать безопасную стартовую позицию в открытом мире (желательно прибрежную), перейти к участку дороги на существенно большую дистанцию, найти доступные настоящие дорожные предметы и **действительно** выполнить игровой лут. Это не сценарий обхода монумента. Итог — реальные перемещения, реальные сущности, реальные предметы и отчёт с балансом источника/получателя. Никакой постановочной телепортации.

**Философия проекта:** конечная цель 50–100 постоянных самостоятельных выживших на личном соло-сервере Rust; полноценные NPC-персонажи, бомжи на пляжах, дороги/ресурсы/бочки/ящики/карточки/RT, крафт, верстаки и чертежи, собственные базы с TC и upkeep, спалки и respawn, кланы и ганг-войны, оборона/рейды, ограниченная конкуренция за Giant Excavator. Нефтянки/карго не обязательны; Semantic Pack — поздний этап. Подробности в `LIFE_ROADMAP.md`. В 003 НЕ реализовывать весь проект.

## 2. Сначала исследование API, затем минимальная реализация

Сделай небольшой `API_FEASIBILITY.md` на основании ТЕКУЩИХ локальных DLL / реального состояния. Проверить:

1. Геометрию/объекты дорог, кромки карты и берегов, topology/road paths, их связь с RustNav. Не использовать дороги и монументы как ограничивающие зоны появления, а как цели.
2. Достижимость и физическую пригодность точки рождения (shoreline допустима, но не в воде, скале/текстурах, не внутри зданий), выбор долгосрочной outdoor-цели в 150–300+ м; разбивку на короткие проверенные сегменты; устранение прогресс-фальшивок и stuck/repath.
3. Фактические server types префабов дорожной бочки и придорожного лут-контейнера в установленном manifest; жизненный цикл spawn, native loot/drop, containers, получение/передача Item. Проверить совместимость с установленными Oxide DLL; не угадывать названия классов и хуков.
4. Можно ли осмысленно связать выбранный NPC со штатным `BasePlayer`/native inventory и как сохранять инвентарь между server restart. Отдельно сравнить вариант Gen2 navigation+проверяемое bot-owned ItemContainer со штатным PlayerInventory. Не создавать поддельных Steam-аккаунтов. Выбрать наименьший риск и явно документировать ограничения визуальной экипировки.
5. Native нанесение урона бочкам/взаимодействие с ящиками на физически близкой дистанции. Нельзя засчитывать `Kill()` бочки и прямое создание готовых ресурсов как доказательство, что бот ударил и полутал.

Изучить 1–2 ближайших рабочих исходника из репы и локальных API перед архитектурой. Изменения исходников — по минимуму, поверх работающего 001; не ломать его regression proof и не превращать тестовый probe в production AI. Новые системы лучше в `src/plugins/` + общие helpers, насколько поддерживает Oxide компиляция.

## 3. Инженерный объём 003

### A. Дальнее путешествие по открытому миру

Разработай ограниченный **WorldTravel** на одном NPC с выбором нескольких динамических локальных целей по пути к outdoor-цели около дороги. Проверяй NavMesh readiness, agent type, `PathComplete` для каждого сегмента, фактическое смещение, скорость, длину пути, стабилизацию после stuck, своевременную перестройку/альтернативу, отказ без бесконечного цикла. Не считать изменение `transform.position` вследствие прямого warp настоящим перемещением. Добираться к цели через несколько шагов с измерениями; не полагаться на монументы как waypoint-only клетки. Не требуется полная карта дорог, но нужен первый реальный road-adjacent маршрут.

### B. Первое настоящее взаимодействие с предметами

Реализовать минимальный адаптер действия `Approach → Interact → Verify` для **двух** классов возможностей: (i) бочка с настоящей добычей, (ii) дорожный контейнер/ящик с настоящим loot inventory. Приоритет — реально существующие в мире сущности; если чистая тестовая карта не содержит безопасно доступных экземпляров, можно **только в изолированном E2E** создать документированный настоящий prefab, с native loot initialization, на доступной физической поверхности. Лог должен явно помечать `NATURAL` или `FIXTURE_NATIVE_PREFAB` — не выдавать специально созданную бочку за естественный roadside spawn.

Действия проводить в физической досягаемости (проверить расстояние, line-of-sight/доступ, права); записывать net contents до/после. Если native PlayerInventory невозможен у Gen2, реализовать проверяемое owned bot inventory с реальными `Item`/`ItemContainer` и четким описанием ограничений. Не создавать items на пустом месте, не телепортировать предметы из далёких контейнеров. Предпочтительнее доказать crate + inventory, чем притвориться, будто бой бочки уже работает. Реальные dropped items, контейнеры и server item transfer должны быть сохранны/не дублироваться. Если предметов нет по штатным правилам дропа, честный PARTIAL, а не подложенный ресурс.

### C. Совместимость и ограничение сложности

Ни строительства/дверей/шкафов, ни PvP, ни крафта, ни respawn, ни кланов, ни Big Excavator в 003. Не обещать эти возможности от лица тестового `ScientistNPC2`. Не делать 50–100 active NPC, не строить полноформатный cognitive framework. Можно добавить лёгкую границу для будущих `BotIdentity`, `WorldGoal`, `InventoryAdapter`, но без переусложнения.

### D. Автоматический E2E и безопасность

Codex сам запускает все тесты; пользователь не открывает игру и не вводит PowerShell. Существующий runner/harness и физический кеш по возможности **переиспользовать**, не копировать тяжёлые папки сервера и не генерировать карту при каждом запуске. Firewall isolated (если system helper требует один системный consent, не обходить), owned-process Job Object, отдельные writable Oxide/config/data, свежие секреты/порты/identity test scope; owner `Server/` остаётся неизменным, кроме отдельно санкционированных копий наших новых плагинов (их установка необязательна; не трогать чужие). Игра отключена от внешней сети во время E2E; ошибки MapCache upload ожидаемы. Не повышать RustDedicated до Administrator, если этого не требует Windows. Не убивать посторонние процессы, не искать PID по имени ради остановки. Cleanup даже при ошибках, проверка отсутствия owned processes, портов, firewall rules и замков. Не удалять старые логи/кеши без отдельного approval; можно задокументировать cleanup.

Минимальная проверка: offline C# 7.3 against installed binaries (не равно live pass), PS tests; затем реальный Oxide plugin compile/load; один extended live server E2E (повторный — при обоснованной корректировке, максимум разумное число, не бесконечные прогоны). Статусы каждой отдельной части OPEN_TRAVEL / BARREL / CRATE / INVENTORY: `GREEN`, `PARTIAL` или `BLOCKED` с raw evidence.

## 4. Приёмка (подробности в ACCEPTANCE.md)

Для **полного GREEN** обязательно одновременно:
- один естественно двигающийся humanoid NPC, spawn в безопасном месте, validated RustNav, длинный outdoor journey с измеренным суммарным ходом >=250 м и хотя бы один переход от >=75 м (допустимо разбиение на локальные `PathComplete` сегменты; фактическое net displacement и абсолютные расстояния согласованы), waypoint около настоящей дороги, без прямых warps;
- успешные физические interactions: одна native loot crate (перемещён >=1 реальный Item из источника в owned inventory без дупа), одна настоящая бочка уничтожена **доказанным игровым уроном** и >=1 реальный выпавший Item извлечён, либо отдельно фиксируется невозможность/отсутствие лута как PARTIAL;
- true item conservation в тестовом scope: item ids/amounts, source-minus, dest-plus, никакого `GiveItem`, чит-спавна ресурсов, принудительного добавления предметов для прохода; native prefabs, если созданные тестом, не копят дубликаты и убираются;
- live Oxide compiled; log и JSON receipts, после test clear shutdown (PID/ports/firewall), отсутствие изменений пользовательского мира/конфигов; никакой `Server/` в Git; commit+push `origin/master` без force.

Если часть действительно недостижима при установленном API — честный PARTIAL/BLOCKED с кодом/данными и перечнем следующего шага; нельзя снижать критерии по-тихому, выдавать one-room movement за world travel или stack count за native pickup.

## 5. Публикация

Весь исходный код и безопасная документация — в публичном репозитории. Не выносить реальные конфиги/saves/secrets/steam IDs в Git, `git add .` не применять; перед `add` проверить effective ignores, `git ls-files -- Server/`, `diff --check`, source/UTF-8, BOM/escaped Cyrillic/mojibake. Зафиксировать точные пути и diff, `git commit`, обычный `git push origin master` (fast-forward, NO force). Git actions в этой задаче явно разрешены; если расходится HEAD или есть чужие изменения — не стирать, не делать reset/stash/clean. Отчёт `RESULT.md` с живой телеметрией и всеми ограничениями; последний SHA сверить с `origin/master`.

## 6. Стоп-условия

Отсутствует native path/чистый E2E после ограниченных диагностических прогонов, не хватает прав на isolated firewall, явная угроза owner миру/конфигам, неизвестные API без верификации, stale runtime cache, невозможность реального сохранного transfer. В таких случаях не обходить безопасность и не имитировать успех. Завершить честным отчетом и безопасным shutdown.
